> 只做标题层级调整；目标与边界见 [`任务书.md`](./任务书.md)，首轮交付物见 [`待办与规划.md`](./待办与规划.md)。

## 先审查现有别名语义

分别梳理各项目的别名来源、优先级、自定义配置、缓存、监听与刷新机制，以及真实调用方。

重点明确：

1. 如何区分游戏、实体类型、标准名称、无匹配与多义匹配。
2. 多来源别名、自定义覆盖、删除自定义项后恢复默认值的规则。
3. 数据变更后如何刷新缓存，如何处理并发读取与更新。
4. API 如何表达精确别名命中、歧义及必要的匹配信息。
5. 服务版本与调用方的兼容策略，以及服务缺失、未就绪或初始化失败时的降级行为。
6. 哪些逻辑属于共享别名能力，哪些必须继续由业务插件负责。

Atlas 的来源分层、Meta 的多命中处理，以及 ProfileImg 的目录存在性检查、角色归一和文件监听均需单独核实。共享服务不能擅自接管图库目录检查、页面路由、业务归一等专属逻辑。

Axiu-Plugin 暂不列为首批迁移对象，除非实际检查发现明确的文本别名需求。

先产出 API 契约草案、现有行为对照表、潜在兼容破坏清单。不要仅根据模块名称推断功能，也不要提前编写适配层。

## 设计统一安装引导机制

目标是让业务插件在 Alias-Plugin 缺失时能够触发统一引导安装，同时保证自身功能在依赖暂不可用时仍能正常加载。

预期方向：

- Alias-Plugin 仓库统一维护唯一的引导单 JS 插件范例。
- 业务插件复用同一范例，不各自维护下载、重试和清理实现。
- 引导插件投放到 TRSS-Yunzai 的 `plugins/example/`；先核实当前框架对该目录、扫描和导入时序的实际处理。
- 引导器只负责安装缺失的 Alias-Plugin，不自动更新已有安装。
- 不假定文件投放后会在当前启动周期执行，也不假定下载完成后服务已经在当前进程中就绪。
- 不因依赖缺失、安装失败或服务初始化失败而阻断业务插件整体加载。

必须明确首次获取引导范例失败后的恢复路径。区分引导文件投放、引导插件实际加载、服务安装完成、服务版本兼容、当前进程服务就绪等状态，并使日志与真实状态一致。

引导范例与服务安装包应使用可复现的版本来源，并具备合理的内容完整性和可信来源验证。不能把固定下载地址等同于固定版本，也不能只凭目录或入口文件存在就判断安装完整。

## 安装事务与恢复要求

在设计中覆盖以下情况：

- 多个业务插件同时发现依赖缺失，重复投放引导文件。
- 多次 cron 触发、下载长时间未结束、超时或异常。
- 下载中断、验证前中断、发布前中断以及重启恢复。
- 安装期间其他执行者已完成安装。
- 目标目录已存在用户内容、权限不足或清理失败。
- 已安装版本不兼容，或服务文件完整但初始化失败。

要求安装过程具有明确的事务边界、并发互斥、完整性验证、暂存与发布策略及崩溃恢复规则。暂存内容不得被框架误当作正式插件加载；发布前重新检查目标状态。只清理能够确认由本机制创建且仍归本机制所有的临时内容。

先确定项目支持的并发范围。若只支持单个 Yunzai 进程，应明确记录；若需要支持多个进程共享同一 bot 目录，则必须另行设计文件级互斥。

引导插件删除自身文件，不代表已注册的定时任务必然停止。必须分别设计任务停止、文件清理和失败恢复，并检查服务入口与引导插件在同次扫描中并发加载的风险。

## 联网与文件系统约束

明确区分别名查询、首次依赖安装和服务数据更新三种联网行为。

检查 Meta 等现有项目的联网开关、运行时写目录限制及相关硬约束，明确它们对迁移后的调用方和引导机制分别有什么影响。不得借安装流程绕过业务配置或已有约束。

已有完整安装不应每次启动都重复下载；版本不兼容时保留现有安装、提示原因并等待明确的处理策略，不得擅自覆盖。

## 验收设计

在实施前建立测试矩阵，至少覆盖：

1. 服务缺失时，首次投放、引导实际加载、安装完成和服务就绪的时序。
2. `plugins/example/` 不存在、为空、已有其他 JS 文件等情况。
3. 多个业务插件并发触发，且携带不同范例版本时的确定性处理。
4. 首次引导获取失败、网络恢复、下载失败与后续重试。
5. 长任务跨越多个 cron 周期、超时、异常与锁释放。
6. 下载和发布过程中的进程中断、重启恢复及半成品隔离。
7. 用户已有文件、目标安装竞争、权限不足和清理失败。
8. 服务未注册、尚未就绪、初始化失败及版本不兼容时的降级。
9. 引导任务停止、服务与引导并发加载及重复安装防护。
10. 跨游戏、跨实体、多义别名、自定义覆盖与删除、缓存刷新及业务专属边界。
11. 联网关闭、受限写目录和已有完整安装时的行为。

这些是验收要求，不是已通过的测试。不得将设计完成等同于实现正确。
